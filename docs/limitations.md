# 현재 제한과 알려진 문제

이 문서는 개발 단계 구현의 경계입니다. 테스트 통과는 배포 인증이나 모든 저장소에서의 무결성·성능 보증이 아닙니다.

## 아직 지원하지 않는 기능

- Windows/Linux 네이티브 GUI.
- 제공자 OAuth·PR API, 강제 push, 변경 되돌리기(discard), merge·rebase·충돌 해결 UI. 공통 SSH/HTTPS clone·fetch·빨리 감기 pull·단일 브랜치 push는 지원합니다.
- 일반적인 branch CRUD·checkout UI, history rewriting, 임의 행 스테이징. 브랜치 생성은 현재 Task 준비 과정에서만 지원합니다.
- Stash 적용·삭제. 현재 Stash는 목록·파일·Diff 읽기 전용입니다.
- GUI에서 다중 저장소·그룹·recipe·trust를 자유롭게 편집하는 기능.
- AI 도구 직접 실행, MCP 연결, 자동 CI·빌드·테스트·병합.
- 일반적인 실제 Xcode 프로젝트 편집. 첫 iOS adapter는 합성 FixtureApp/Debug의 xcconfig 두 key만 지원합니다.

## 배포·호환성

- `0.1.0-alpha.10`는 Apple Silicon(arm64)용 사전 릴리스 DMG입니다. Intel·universal2 공개 빌드는 없습니다. [다운로드와 설치 방법](../README.ko.md#macos에-설치하기)을 확인하세요.
- 선언된 최소 대상은 macOS 14이지만 실행 검증은 macOS 27.0.1에서만 했습니다. macOS 14–26에서의 호환성은 아직 검증하지 않았습니다.
- 앱과 Rust 엔진은 함께 배포하지만 Git은 포함하지 않습니다. 런타임은 `/usr/bin:/bin:/usr/sbin:/sbin` 경로를 사용하므로 Apple Command Line Tools 또는 Xcode의 Git이 필요합니다. Homebrew 전용 경로의 Git은 사용하지 않습니다. 내장 예제의 준비 스크립트는 `python3`도 실행합니다.
- 공개 DMG의 서명과 Apple notarization 상태는 [릴리스 정보](releases/v0.1.0-alpha.10.md)에 기록합니다. 로컬 빌드의 기본 ad-hoc 서명과 혼동하지 마세요. notarization이 완료되지 않은 앱은 macOS의 실행 확인에 막힐 수 있습니다.
- alpha.6부터 새 버전을 자동 확인하며 River 메뉴에서 직접 확인할 수도 있습니다. 다운로드·설치·재시작은 사용자가 선택합니다. 실행 중 작업은 재시작을 막으며, 임시 입력과 응답 불명 작업은 확인 안내를 표시합니다. 종료 정리 중 새 상태 때문에 재시작이 취소되면 연결을 다시 열어야 할 수 있습니다. alpha.5 이하는 현재 DMG를 한 번 직접 설치해야 합니다. [업데이트 안내](updates.md)를 참고하세요.
- 업데이트 피드·서명·버전 확인과 OS가 진행하는 실제 설치·재시작은 별도입니다. OS가 진행하는 업데이트 설치·재시작 검증은 완료하지 않았습니다.
- 라이선스는 미확정이며 현재 Cargo 메타데이터는 `UNLICENSED`입니다.

## Git·준비 정책

- Git fsmonitor·hook·외부 서명 프로그램을 실행하지 않습니다. 앱 커밋에는 hook이 적용되지 않고, `commit.gpgsign=true`여도 서명하지 않습니다.
- 상태·Diff·Git 위생 검사에는 속성 조회를 격리할 수 있는 Apple Git 2.43 이상이 필요합니다. 오래된 Git에서는 Xcode 또는 Command Line Tools 업데이트 안내를 표시합니다.
- 일반 파일 전체 스테이징에는 속성 변환을 격리할 수 있는 Git 2.42 이상이 필요합니다. 오래된 Git은 업데이트 안내와 함께 중단하며, 스테이징 취소·삭제·심볼릭 링크에는 이 변환 요구가 적용되지 않습니다. 안전하게 재현할 수 없는 변환 속성도 명시적으로 거부합니다.
- 외부 clean/smudge/process 필터 설정이 있으면 명시적으로 중단합니다. LFS나 사용하지 않는 전역 필터도 현재 제한에 포함됩니다.
- 파일 전체 스테이징의 내용 변환과 일반 상태·Diff·Git 위생 검사는 각각 별도 Git 설정·속성 환경에서 처리합니다. 조회는 요청마다 index·HEAD·ref·적용 속성을 고정하고 실제 작업 폴더와 객체 저장소를 읽으며, 반환 전에 원본 구성을 재확인합니다. 외부 필터 정의와 include를 내용 조회 프로세스에 전달하지 않습니다. 작업 폴더 생성·커밋·checkout 등 실제 저장소 쓰기는 설정 검사와 실행 사이의 동시 변경까지 격리하지 않으며, 모든 Git 명령의 격리를 보장하는 것은 아닙니다.
- 격리 조회는 index 및 split-index 의존 파일 각각 64 MiB, 설정 1 MiB, 개별 속성·ignore 파일 1 MiB, 수집 원본 합계 8 MiB, 적용 디렉터리 16,384개·깊이 128단계로 제한합니다. 지원할 수 없는 구성이면 조회를 중단합니다. 원본 index나 작업 파일을 조회용으로 정규화하지 않습니다.
- 서브모듈·특수 파일 준비와 일부 인코딩은 지원하지 않습니다. 올바른 UTF-8로 해석할 수 없는 Diff는 경고를 표시하며 hunk staging·개인 검토 표시·수정 요청에 쓰지 않습니다.
- Source-plan drift·신뢰 변경·canonical worktree 불일치는 중단 사유입니다. 자동 재계획·reset·clean·강제 삭제로 복구하지 않습니다.
- 준비 worker에는 저장소별 예산과 읽기 단계별 최대 30초 제한을 적용하며, 파일 열거·64 KiB 단위 읽기·Git 프로세스 대기 중 취소를 확인합니다. 이미 접수한 쓰기는 별도 제한 안에서 결과를 확인합니다. 취소는 rollback을 뜻하지 않으며 기존 브랜치·작업 폴더·완료된 저장소는 남을 수 있습니다. 운영체제 자체의 지연된 파일 I/O가 즉시 종료됨을 보장하지는 않습니다.
- Recipe는 OS sandbox가 아닙니다. 저장소 간 원자적 commit/rollback, process group을 벗어난 자식, 모든 비멱등 script의 안전성을 보장하지 않습니다.
- 파일 전체 스테이징·취소는 연결된 엔진이 기능을 제공할 때 선택한 파일에만 적용합니다. 새 파일도 명시적으로 스테이징해야 합니다. 전체 취소는 그 파일의 부분 선택까지 해제하며 작업 폴더 내용은 유지합니다. 구형 엔진에 자동 우회 명령을 보내지는 않습니다.
- 파일 전체 스테이징은 파일당 32 MiB·index 64 MiB까지입니다. 충돌, 서브모듈·중첩 저장소, 디렉터리·특수 파일, 안전하지 않은 경로는 거부합니다. 지원하는 심볼릭 링크는 링크 대상 문자열만 다루고 대상을 따라가지 않습니다.
- 새 일반 파일은 가능한 경우 미리보기를 표시합니다. 바이너리·일부 인코딩·파일 종류·권한 변경은 텍스트 hunk 선택과 지원 범위가 다릅니다. 파일 전체 스테이징 가능 여부는 별도로 표시하며, 내용을 확인할 수 없으면 외부 도구에서 확인해야 합니다.
- 일반 staging·commit의 영속 mutation journal과 범용 재시도 idempotency는 후속입니다. 결과가 불명확하면 Git 상태를 확인하고 자동 반복하지 않습니다.

## AI 작업 흐름의 경계

- 상단 **작업·AI 안내**는 기존 **작업 정보** 패널을 엽니다. 현재 checkout에서 목적·완료 조건·근거를 기록할 수 있으며, 별도 Task·브랜치·워크트리는 필수가 아닙니다.
- 요청 초안은 사용자가 확인·수정·복사해 외부 AI 도구에 전달합니다. River가 모델을 호출하거나 자료를 자동 전송하거나 AI-DLC 전체 단계를 실행하지 않습니다.
- 결과와 증거 위치는 사람이 적거나 AI 답변을 옮긴 보고입니다. 조건 연결·통과 상태·일치하는 코드 해시·문서 버전 고정은 실제 실행 관찰, 조건 충족, 단계 승인이나 병합 준비를 인증하지 않습니다. 확인하지 못한 코드 상태는 비워 둡니다.
- 앱의 Git 검사는 추적 파일의 공백·충돌·진행 상태에 한정됩니다. 빌드·테스트·실제 기능 사용, 추적되지 않은 내용·서브모듈 검증은 별도로 수행해야 합니다. [첫 사용 예제](getting-started.md)와 [작업 흐름](task-workflow.md)을 참고하세요.

## 원격 Git

- GitHub·GitLab·Bitbucket·자체 서버에 공통 SSH/HTTPS를 사용하며 Apple Git 2.41 이상이 필요합니다. 제공자별 로그인·토큰 입력·PR 기능은 없습니다. 인증은 기존 SSH agent·기본 키·known-host 파일 또는 Apple Git 키체인 helper에서 준비해야 합니다.
- 사용자 SSH config·별칭·ProxyCommand·임의 identity 경로, 대화형 인증, 임의 credential helper는 사용하지 않습니다. 파일 경로·`file://`·`git://`·외부 remote helper·URL rewrite·방향별 복수 URL·partial/promisor 저장소와 보안을 바꾸는 HTTP 설정은 거부합니다.
- 등록된 저장소 이름에 탭·줄바꿈 같은 제어문자가 들어 있으면 원격 작업은 현재 지원하지 않습니다. Git 경로의 공백은 보존하지만, 경로를 등록 이름으로 만드는 정책과 원격 ID 검증의 통합은 후속입니다.
- Fetch는 선택 원격의 브랜치 head만 갱신·prune합니다. 태그·서브모듈 동기화는 포함하지 않습니다. Pull은 깨끗한 폴더에서 빨리 감기로만, push는 확인한 commit을 한 브랜치로만 전송합니다.
- 원격 설정과 추적 ref는 연결된 worktree에 공유됩니다. 확인 이후 URL·로컬 상태·원격 ref가 바뀌면 재확인이 필요합니다. 응답을 잃거나 시간이 초과되면 Git과 서버 상태를 확인하기 전 재시도하지 마세요. 클라이언트를 닫아도 서버 작업 취소가 확정되는 것은 아닙니다.
- Clone bootstrap helper가 강제 종료되면 별도 process group의 Git 자식이 계속 실행되거나 대상 옆의 앱 소유 staging 폴더가 남을 수 있습니다. timeout은 모든 자식 종료·정리 완료를 보증하지 않습니다. 종료된 helper가 뒤늦게 staging을 게시할 수는 없지만, 대상·부모 폴더와 Git·서버 상태를 확인하기 전 재시도하지 마세요. 자동 재실행·잔여 폴더 삭제는 하지 않습니다.
- [지원 URL·실행 경계·복구 안내](remotes.md)에서 자세한 정책을 확인하세요.

## 표시·성능 경계

- 그래프와 선택 브랜치 기록은 최대 80개 commit을 표시합니다.
- Diff 표시는 5,000줄·512 KiB로 제한합니다. 큰 응답은 wire 크기 제한으로 실패할 수도 있습니다.
- 개인 검토 checkpoint는 최대 32개·텍스트 합계 4 MiB·개별 512 KiB입니다. 최근 폴더의 review cache는 6개입니다. 세션 초안은 이 cache와 별도로 유지합니다.
- 준비 접수 8개, IPC handler 32개, 직렬 mutation은 서로 다른 제한입니다. 이 수치가 전체 메모리나 UI 응답 시간을 보장하지는 않습니다.
- 폴더 전환 시 이전 클라이언트 조회 대기를 취소해 현재 폴더 검증을 시작합니다. Rich 작업 정보는 기능 확인 이후 한 번의 전용 RPC로 조회하고 값이 같으면 다시 발행하지 않습니다.
- 파일·staged 선택의 빠른 연속 입력은 80ms 동안 묶습니다. 클라이언트가 취소해도 이미 시작한 서버 읽기는 계속될 수 있습니다.
- 패널 확대는 기존 화면 트리를 유지합니다. 숨겨진 브랜치 패널의 조회도 앱 활성 상태에서 계속될 수 있으며, 확대만으로 CPU·메모리 사용이 줄어드는 것은 보장하지 않습니다.
- 방문한 workspace 엔진은 세션 동안 남을 수 있습니다. 많은 저장소를 오갈 때의 RSS·에너지·복귀 시간은 아직 측정하지 않았습니다.
- 패널을 크게 볼 때 숨겨진 입력을 차단하기 위해 키보드 포커스를 정리합니다. 계속 보이는 입력란도 확대 직후에는 다시 선택해야 할 수 있습니다. 확대된 패널에서 사용자가 선택한 편집기 포커스는 원래 배치로 돌아갈 때 유지합니다.
- 큰 journal에서 최초 JSON index 생성이 엔진의 시작 대기 시간을 넘을 가능성, 큰 파일 snapshot·checkpoint 저장 비용도 계측 과제입니다.

## 복구·조회 동작과 남은 UX 과제

2026-10-22 전체 검토에서 연결·준비 상태와 수동 새로고침을 보강했습니다.

- 새 프로젝트 연결 확인에 실패하면 이전 프로젝트의 연결·표시·초안을 함께 유지합니다. 서로 다른 프로젝트의 표시와 쓰기 대상이 섞이지 않도록 합니다.
- 작업 실행 요청 뒤 응답을 잃으면 원래 프로젝트 이름·경로와 실행 여부 확인 안내를 앱 세션에 남깁니다. 작업 목록과 실제 Git 상태를 확인해야 하며, 자동 재실행이나 재시작 이후의 안내 복원은 지원하지 않습니다.
- 작업 정보 조회 실패 시 준비·재시도·복구용 새 작업 동작을 제한하고 실패 안내를 표시합니다. 이미 실행 중인 것으로 알려진 작업의 명시적 취소는 계속 허용하며 서비스가 현재 상태를 확인합니다.
- 같은 프로젝트 재연결은 입력한 새 작업 이름·브랜치·방식을 유지하고 기존 계획만 무효화합니다. 만료된 계획도 입력을 유지한 채 미리보기로 돌아가며 실행 전 계획을 다시 확인해야 합니다. 원본 변경·브랜치 이름 충돌은 변경된 이유를 설명하고 새 작업 계획으로 안내합니다.
- 캐시가 없는 첫 조회는 로딩 표시를 사용하며, 확인된 변경 없음·준비 전 폴더·조회 실패를 구분합니다. 캐시가 있으면 검증 중에도 읽기 전용으로 유지합니다.
- Git 속성·Diff 설정만 바뀌면 자동 polling의 파일 snapshot이 같을 수 있습니다. 수동 새로고침은 선택한 Diff도 다시 읽습니다.
- 브랜치 기록은 제목과 작성자·커밋 ID를 두 줄로 표시합니다. 매우 좁은 pane의 세로 목록 크기와 배치 방향 전환 시 스크롤·divider 유지는 후속입니다.

## 등록·복구

최근 메뉴와 workspace 등록은 별도입니다. 정상 등록은 메뉴에서 빠져도 다시 찾습니다. 최근 메뉴 갱신은 앱 인스턴스 사이에서 잠금으로 직렬화합니다. 손상된 최근 메뉴는 같은 잠금 안에서 다시 확인한 뒤 보존·재구성합니다.

- 알려진 workspace의 설정 파일이 사라지면 journal을 새 workspace로 조용히 대체하지 않고 실패합니다. 현재 다시 열라는 안내만으로 해결되지 않을 수 있으며, 기존 설정을 복구해야 합니다.
- 읽을 수 있지만 JSON이 잘못되었거나 UUID가 맞지 않는 kind record는 유효한 기존 설정을 통해 같은 workspace UUID와 journal을 찾습니다.
- 안전하게 읽을 수 없는 kind record는 해당 항목 전체를 건너뜁니다. 그 항목이 복원하려던 workspace라면 기존 journal을 찾지 못하고 새 등록을 만들 수 있습니다. 손상된 등록의 자동 복구·병합 UI는 없습니다.
- 저장소 폴더를 이동하거나 이름을 바꾸면 기존 경로의 등록을 자동 이전하지 않습니다. 새 경로를 열면 별도 workspace와 journal을 만들 수 있으며 기존 journal은 남습니다. 기존 Task가 기록한 경로까지 자동으로 고치는 기능은 없습니다.

OS 마우스·키보드 입력과 VoiceOver, macOS 14 실행, 대형 실제 저장소 성능은 별도 검증이 필요합니다.
