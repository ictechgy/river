# AI와 함께 개발할 때 River가 맡을 역할

2026-10-25 조사·제품 결정과 후속 구현. River의 우선 역할은 **작업 의도, 현재 변경, 실제 검증, 다음 확인을 이어 주는 것**이다. 기존 Git 화면과 작업용 폴더를 중심에 두고 필요한 정보를 작업 정보 패널에서 펼쳐 본다.

## 조사에서 얻은 기준

AWS의 AI-DLC는 AI가 작업을 구체화하고 실행하는 동안 사람이 의도와 중요한 선택을 검증하며, 앞 단계의 맥락이 다음 작업에 이어지도록 한다. 적응형 워크플로는 작업에 필요한 단계와 깊이를 선택한다. River에 적용할 판단은 짧은 버그 수정에도 긴 단계표를 강제하기보다, 목적·완료 조건·증거가 끊기는 지점을 보여 주는 것이다. [AWS AI-DLC 소개](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/), [적응형 워크플로](https://aws.amazon.com/blogs/devops/open-sourcing-adaptive-workflows-for-ai-driven-development-life-cycle-ai-dlc/).

Lauren Tan은 자신의 pstack을 엄격한 엔지니어링과 검증을 위한 도구로 설명하고, 해결할 문제를 찾는 바깥 흐름과 구현·검증 흐름을 구분한다. 개인이 보고한 PR 수는 River의 성능 목표나 품질 지표로 사용하지 않는다. [본인 설명](https://www.linkedin.com/posts/laurenelizabethtan_cloud-agents-and-cursor-harness-improvements-activity-7495972438262853632-bLQ5).

Cursor의 pstack 검증 가이드는 관찰 가능한 완료 조건, 실제 산출물 사용, 확인 가능한 증거를 강조한다. 프로젝트 검증 절차는 실행 준비·환경 확인·기능 사용·증거 수집·정리와 기능 지도를 갖추고, 앱이 바뀌면 유지해야 한다. 이를 River에 적용하면 “AI가 통과했다고 했다”를 넘어 어떤 코드에서 무엇을 실제로 확인했는지가 보여야 한다. [고정한 검증 가이드](https://github.com/cursor/plugins/blob/99b609a72323b70204eab407c622f436e858e112/pstack/docs/guide/06-verify-and-ship.md), [pstack 원본](https://github.com/cursor/plugins/blob/99b609a72323b70204eab407c622f436e858e112/pstack/README.md).

아래 우선순위와 UI 선택은 이 자료를 River에 적용한 제품 판단이다.

## 이번에 보강한 흐름

1. **현재 폴더에서 다음에 확인할 일.** 작업 정보의 검증 영역은 목적·완료 조건 누락, 미조회, 최근 앱 검사, 실패·불확실, 코드·완료 조건 변경을 요약한다. 기록 시각이 뒤로 가도 저널의 최신 기록을 기준으로 삼는다. 다른 저장소나 원래 폴더의 통과를 현재 작업용 폴더에 적용하지 않는다.
2. **세부 이력은 펼쳐서 보기.** 기본 화면에는 현재 상태와 다음 확인을 남기고, 명령·출력·이전 기록은 펼친다. 조회한 전체 최근 기록 수와 현재 폴더 기록 수를 표시한다. 최근 50개에 없다는 사실을 전체 이력에 없다는 뜻으로 해석하지 않는다.
3. **같은 판단을 인수인계에도 전달.** 저장소별 코드 상태와 검증 요약, 다음 확인을 함께 모은다. 준비 전 폴더나 조회에 실패한 저장소는 미확인 상태로 남으며, 다른 저장소의 성공으로 채우지 않는다.
4. **실제 동작을 확인하는 요청.** 기존 복사 동작에서 인수인계 또는 검증 요청을 선택한다. 검증 요청은 완료 조건별 확인 방법·실제 결과·코드 상태·증거 위치와 미실행 이유를 요구한다. 내용을 미리 보고 수정한 뒤 사용 중인 AI 도구에 복사한다. River가 AI를 호출하거나 명령을 실행하지 않는다.

이후 사용자 요청에 따라 다음 세 우선순위도 구현했다.

5. **완료 조건별 명시적 연결.** 각 조건에 안정적인 ID와 버전을 부여한다. 수정은 같은 ID의 새 버전, 이동은 같은 ID·버전, 복제는 새 ID가 된다. 보고를 기록할 때 현재 조건을 직접 선택하며, 연결 당시 문구·버전을 보존한다. 삭제·변경 후에도 과거 기록은 남는다. 다른 조건의 수정이나 순서 변경으로 관련 없는 연결을 무효화하지 않는다.
6. **검토했다고 보고한 코드 상태 구분.** 보고자가 명시한 HEAD·변경 상태, 제공자·모델·근거 위치·완료 상태를 별도로 기록한다. 앱이 기록할 때 관찰한 상태를 검토 대상이라고 대신 채우지 않는다. 미완료·도구 오류·완료 여부 미확인과 누락된 검토 상태를 표시하며, 연결이나 통과 보고를 조건 충족·승인으로 승격하지 않는다.
7. **저장소별 검증 절차·기능 지도.** 저장소와 상대 경로를 지정하고, 사용자가 ‘읽기’를 눌러 제한된 일반 텍스트를 확인한다. 읽은 바이트의 SHA-256을 기준으로 저장하는 동작은 별도다. 고정한 해시와 다른 파일은 변경으로 표시하지만, 문서를 읽었다는 이유로 절차를 실행·준수했다고 판단하지 않는다. 내용은 인수인계에 자동으로 포함하지 않는다.

기존 작업 정보 패널의 행·접기·편집 창을 확장했으며 새 상시 대시보드를 추가하지 않았다. 사용 방법과 호환성 범위는 [Task workflow](task-workflow.md)에 정리했다.

예를 들어 앱 검사를 통과한 뒤 코드가 바뀌면 이전 통과를 현재 결과로 보여 주지 않는다. 사용자는 다음 확인을 보고 최신 상태를 검사하거나 검증 요청을 복사한다. AI가 테스트 통과를 보고하더라도 앱이 실행을 관찰한 Git 검사와 구분해 남는다.

## 기록이 뜻하는 범위

- 앱 검사는 추적 파일·스테이징의 공백, 충돌 마커와 진행 중 Git 상태만 확인한다. 빌드·테스트·새 파일·서브모듈 내용·완료 조건 충족·병합 승인을 증명하지 않는다.
- 완료 조건은 작성자의 판단 기준이며 안정적인 ID·버전과 명시적 보고 연결을 갖는다. 연결은 근거를 찾는 수단이며 조건 충족률이나 병합 승인 점수가 아니다. 이전 기록에는 조건을 추측해서 연결하지 않는다.
- AI/직접 보고에는 기록 시점의 앱 관찰과 보고자가 주장한 검토 상태가 따로 남는다. 보고자의 상태를 비워 두면 미기재로 남으며, 어느 쪽도 실제 실행·검토를 인증하지 않는다. 미완료·도구 오류·완료 여부 미확인 보고는 검토 완료의 근거로 취급하지 않는다.
- 인수인계는 저장소별 개별 시점의 관찰이다. 통합 테스트나 작업 전체의 승인으로 사용하지 않는다. 초안을 만드는 동안 바뀐 맥락은 경고하며, 전달 전에 현재 상태를 다시 확인해야 한다.
- 일반 참고·근거 링크의 내용은 읽지 않는다. 검증 절차·기능 지도는 사용자가 저장소별 ‘읽기’를 눌렀을 때만 안전한 상대 경로의 UTF-8 `.md`·`.txt`·`.mdc`·`.rst` 파일을 최대 64 KiB 읽는다. 읽기와 기준 해시 저장은 별도이며 문서 내용·명령을 자동 전송·복사·실행하지 않는다.
- 검증과 조건 연결 조회는 작업 맥락의 최근 50개 기록으로 제한된다. 저장소별 인수인계는 그 안의 최근 5개를 포함한다. 과거 맥락 버전 요약 조회는 최근 10개이며, 화면에 없다고 전체 이력에 없다는 뜻은 아니다.

## 우선순위의 구현 상태와 남은 범위

| 우선순위 | 상태 | 남은 판단 |
| --- | --- | --- |
| 완료 조건과 증거의 명시적 연결 | 안정적 ID·버전, 선택한 조건과 보고의 연결, 변경·삭제 후 이력 보존 구현 | 실제 조건 충족은 사람이 보고와 산출물을 확인해야 한다. |
| 실제 검토한 상태와 기록 시점 구분 | 보고자가 명시한 코드 상태·제공자·모델·근거 위치·완료 상태를 별도 저장 | 제공자 실행 관찰·응답 인증은 제공하지 않는다. |
| 프로젝트 검증 절차·기능 지도 연결 | 저장소별 명시적 읽기, 형식·크기 제한, 기준 해시 저장·변경 표시 구현 | 문서를 실행하거나 해당 절차의 준수를 인증하지 않는다. |
| 팀에서 이어받는 작업 묶음 | 인수인계·검증 요청 초안을 미리 보고 복사 가능 | 묶음 파일 내보내기·공유·권한 모델은 후속 설계가 필요하다. |
| 운영 결과로 다음 작업 찾기 | 근거 위치를 작성자 참조로 보관 가능 | PR·CI·preview·장애 상태의 자동 수집은 외부 권한과 코드 귀속을 먼저 정해야 한다. |

조건 문자열이나 노트에 임시 태그를 붙이는 방식은 중복 조건·재정렬·위조를 안정적으로 다루지 못해 채택하지 않았다. 준비 완료 상태도 구현 완료나 AI-DLC 단계 승인으로 재사용하지 않는다.

## 실제 외부 자문과 이견

Claude, Grok, Devin에게 같은 공개 자료와 River의 현재 기능을 주고 독립 의견을 받은 뒤, 상대 의견과 작은 구현안을 전달해 재논의했다. 이는 제품 자문이며 사용자 조사나 최종 코드 승인과 구분한다.

- Claude는 조건별 근거 연결을 장기 우선순위로 삼았다. 후속 토론에서는 먼저 근거 요약을 만들고, 요청 종류는 분리하거나 인수인계·검증 두 가지로 제한하라고 권했다.
- Grok은 기존 패널의 근거 요약과 인수인계만 먼저 구현하고 목적별 메뉴는 미루자고 했다. 이 의견은 기본 화면을 줄이고 새 패널·프로토콜을 만들지 않는 데 반영했다.
- Devin은 기존 복사 버튼의 목적 선택도 작은 개선으로 보았다. 실행하는 기능으로 오인하지 않도록 ‘검증 요청’이라는 표현을 권했다.
- Agy는 실제 두 호출 모두 사용량 제한 HTTP 429와 출력 토큰 0을 반환했다. 유효한 의견을 받지 못했으며, 완료된 자문으로 합산하지 않았다.

당시 첫 구현은 근거 요약·작은 기본 화면·저장소별 인수인계와 두 가지 초안으로 한정했다. 이후 사용자의 우선순위 구현 요청으로 안정적인 조건 연결·검토 상태·문서 참조를 추가했다. 5종 목적 메뉴와 임시 조건 태그는 계속 제외한다. 위 자문을 이번 후속 구현의 코드 승인으로 재사용하지 않는다. 자문은 현재 설치된 CLI와 설정된 모델로 수행했으며, 호출·프롬프트 해시·원본 응답·오류는 로컬 개발 기록에 각각 보관했다.
