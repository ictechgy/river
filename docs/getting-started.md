# 실제 프로젝트에서 처음 사용하기

작은 변경 하나로 시작하세요. 기존 프로젝트 폴더에서 바로 사용할 수 있고, 새 작업용 폴더나 AI 설정을 먼저 만들 필요는 없습니다.

## 변경을 커밋하기

스테이징은 **이번 커밋에 담을 변경을 고르는 것**입니다. 파일을 수정한 상태와 커밋에 담기로 고른 상태를 따로 보여 줍니다.

1. **저장소 열기…**로 프로젝트를 열고 위쪽에서 저장소·브랜치·폴더를 확인합니다.
2. 파일 목록에서 **스테이징 전**을 선택하고 파일을 누릅니다. Diff에서 변경을 읽습니다.
3. 선택한 파일의 **파일 전체 스테이징**을 누르면 그 파일의 변경을 커밋에 포함합니다. 같은 파일에 여러 작업이 섞였다면 변경 묶음 옆의 **이 변경만 스테이징**을 사용합니다.
4. **커밋에 포함** 목록에서 이번에 담을 내용을 다시 확인합니다. 빼고 싶은 파일은 **파일 전체 스테이징 취소**를 선택합니다. 작업 폴더 내용은 유지됩니다.
5. 위쪽 **커밋 작성**에서 변경 이유를 적고 대상 저장소와 포함된 파일 수를 확인한 뒤 커밋합니다. 다른 파일의 미포함 변경은 그대로 남습니다.

파일 전체 스테이징은 선택한 파일만 대상으로 합니다. 파일 전체 취소는 그 파일에서 이미 골랐던 부분 변경까지 커밋에서 뺍니다. 읽음 표시를 해야 스테이징할 수 있는 것은 아닙니다.

두 목록은 표시 전환이며, 목록 이름을 누르는 것만으로 스테이징하지는 않습니다. 새 파일도 파일 단위로 추가할 수 있습니다. 일반 텍스트 미리보기를 표시하지 못하는 파일은 화면의 이유를 확인하고 외부 편집기에서 내용을 확인하세요. 바이너리는 텍스트 부분 선택 대신 파일 전체 단위로 다룹니다.

버튼이 비활성화되어 있으면 근처의 이유를 먼저 확인합니다. 구형 엔진은 업데이트 후 다시 연결해야 합니다. 일반 파일 전체 스테이징에는 Git 2.42 이상이 필요하며, 이보다 오래된 Git이면 Apple Command Line Tools 또는 Xcode의 Git을 업데이트해야 합니다. 파일 크기·충돌·특수 파일 등 자세한 지원 범위는 [현재 제한](limitations.md#git준비-정책)을 확인하세요.

## AI와 작은 기능 하나 진행하기

예시는 **“로그인 실패 시 이메일 입력을 유지한다”**입니다. 상단 **작업·AI 안내**를 누르면 **작업 정보** 패널에 네 단계가 나타납니다.

| 순서 | 할 일 | 남길 내용 |
| --- | --- | --- |
| 1. 원하는 결과 정하기 | **1. 목적 · 완료 조건** 옆 **작성 · 수정**에서 작성·저장 | 목적: 잘못된 암호를 입력한 뒤 이메일을 다시 입력하지 않아도 된다. 조건: 오류가 보이고 이메일이 유지되며, 암호는 안전하게 처리된다. |
| 2. AI에 맥락 전달하기 | **2. AI 요청 미리보기 · 복사 → 작업 맥락 / AI 요청**에서 초안을 확인·수정하고 **초안 복사**로 전달 | “관련 코드를 살펴보고 수정 계획부터 설명해 줘. 계획을 확인한 뒤 구현하자.” |
| 3. 결과와 근거 남기기 | AI에서 구현한 뒤 River를 새로고침하고 실제 동작 확인. 필요하면 **검증 요청** 초안을 전달하고 **3. 실제 확인 후 결과 · 근거 기록…**에 기록 | 잘못된 암호로 실제 로그인을 시도한 결과, 테스트 결과, 화면이나 로그 위치, 확인하지 못한 부분 |
| 4. 검토하고 커밋하기 | **4. 변경 검토 → 파일 · 스테이징 / 커밋**에서 Diff를 확인하고 의도한 변경만 스테이징·커밋 | 이번 커밋에 담는 변경과 이유, 남은 문제 |

River에서 초안을 복사하면 AI가 자동 실행되는 것은 아닙니다. 현재 쓰는 AI 도구에 직접 전달합니다. 그 도구가 프로젝트를 수정한 다음 River로 돌아와 변경과 근거를 함께 살펴보는 흐름입니다. 결과 기록 창에서는 확인 내용과 근거부터 적습니다. **보고 출처 · 검토한 코드 상태 (선택)**은 필요할 때 열고, 보고자가 검토한 코드 상태를 모르면 빈칸으로 남기세요. River가 기록 시점의 코드를 대신 검토 대상이라고 채우지 않습니다.

완료 조건을 고르거나 통과로 저장해도 보고자의 기록으로 남습니다. River가 조건 충족이나 작업 승인을 판정하지 않습니다. 빌드 성공과 실제 동작 확인은 다릅니다. River의 **공백 · 충돌 마커 검사**는 Git 위생 검사이므로, 로그인 화면을 사용해 봤다는 근거를 대신하지 않습니다. AI가 확인하지 못했다고 답했다면 그 이유를 남기고 다음 확인으로 이어갑니다.

## AI-DLC와 연결되는 부분

AWS는 AI가 계획과 구현을 진행하면서 사람이 중요한 결정을 검토하고 결과를 검증하는 반복을 설명합니다. 작업의 규모에 맞춰 필요한 단계를 선택하는 것도 강조합니다. [AI-DLC 소개](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/), [적응형 워크플로 설명](https://aws.amazon.com/blogs/devops/open-sourcing-adaptive-workflows-for-ai-driven-development-life-cycle-ai-dlc/).

River에서는 **의도·완료 조건 → 작업 중인 브랜치와 변경 → 실제 결과·근거 → 다음 사람이 이어받을 자료**를 연결하는 데 적용합니다. 작은 수정은 위 순서로 짧게 진행하고, 여러 저장소나 병렬 AI 작업이 필요하면 작업용 폴더를 따로 준비할 수 있습니다. 문서를 등록하거나 통과 보고를 적는 것만으로 AI-DLC 단계가 승인되지는 않습니다. AI-DLC 규칙·steering을 쓰는 프로젝트라면 실행은 해당 AI 도구에서 진행하고, River에는 그때의 목적·변경·검증 근거를 이어 남깁니다.

조건 이력·검토 코드 상태·문서 버전 고정의 자세한 범위는 [Task workflow](task-workflow.md)를 참고하세요.
